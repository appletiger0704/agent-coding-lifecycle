# v0.3 — Issue-scoped deterministic lifecycle (P0)

本版只強化 **單一** `agent-coding-lifecycle` Skill；不引入新 Agent、中央資料庫、自動批准或合併權限。

## 核心原則

- **Issue-scoped**：`run` 必須明確指定 Issue number；不可在多 Issue 環境靠猜測選任務。
- **來源可驗證**：GitHub Issue/PR/Checks 用 `gh` 查詢、Git/Worktree 用 `git` 查詢、OpenSpec/ADR 由 Repo 檔案解析。
- **Fail closed**：缺少 `gh`/登入/合約、GitHub 查詢失敗、PR 不相符、未知 ADR 狀態或不完整 CI 均回報 `blocked`。
- **無自動批准**：Status 是事實歸納，不等於人工核准／PR 可以合併。所有寫入、合併與部署仍依原本授權。
- **不宣稱實機驗證**：目前僅是離線 policy / mocked collector 測試；Codex ↔ Claude Code、不同 OpenSpec 版本、GitHub 真實 API 仍待驗收。

## 使用方法

目標產品 Repository 必須有 Git、`gh` CLI（已登入且具備讀取 Issue/PR/Checks 權限）及 Python 3。用完整安裝腳本之後：

```bash
python3 .agents/skills/agent-coding-lifecycle/scripts/status-validator.py --repo . --issue 123
```

或使用中央 Repo 原始腳本：

```bash
python3 skills/agent-coding-lifecycle/scripts/status-validator.py --repo /path/to/product-repo --issue 123
```

預設**只讀取**資料；輸出 JSON：`schema_version`、`issue_number`、`stage`、`next_action`、`blocked`、`blockers`、`evidence`。正常可前進時 exit 0；安全阻擋或資料無法確認時 exit 2。不可把 `--snapshot` 測試模式的結果當作正式決策依據。

## Issue contract

在產品 Repo 建立 `.agent-lifecycle/issues/123.json`，格式範例見 [template](../templates/issue-contract.json)。這是**人員可審查的工作分類與關聯契約**，不是 GitHub Issue 的替代品。

| 欄位 | 說明 |
|---|---|
| `issue_number` | 必須與查詢 Issue 相同 |
| `branch` | 此 Issue 專屬工作分支；Tracked 模式必填，必須與目前 checkout 一致 |
| `type` | `routine`（免新 Spec/ADR）、`feature`（需 OpenSpec）、`architecture`（需 OpenSpec + ADR） |
| `spec_change` | 對應 `openspec/changes/<name>`；feature/architecture 必填 |
| `adr_paths` | 相關 ADR 檔案路徑；新架構決策需明確列出 |
| `required_checks` | PR 預期 CI check 名稱（需與 GitHub Checks 一致） |
| `pr_number` | 有多個 PR 時填入明確 PR；PR 仍須在 GitHub 關聯到 Issue |

流程為 `issue → openspec（條件式）→ adr（條件式）→ implement → pr → CI/review → close`。初期缺 contract 會回 `define_issue_contract`，不自動臆測分類。日常 bugfix 使用 `routine` 以維持輕量；需要重大新決策時必須選 `architecture`，不能為了跳過核准而任意降級。

## Tracked 狀態證據與限制

- 由 `gh repo view` 取得 GitHub 預設分支（不假設 `main`），由 `gh api` 讀取最新 HEAD SHA，與本地 default branch 比較；不自動 `git fetch` 或更動本地 refs。
- 若契約未填 `branch`、checkout 在錯的 Issue 分支、分支落後 default branch，或本地 default branch 仍是舊版，停止並要求同步。
- PR head SHA 與本地同名 branch 需一致；Checks 必須查該 PR SHA，分頁不足時標記未驗證。
- 仍非完整權限／核准閘門：ADR 文件宣告 Accepted 不證明人工核准，PR review／Rulesets 不在此版自動設定。

## 已實作的判定邊界

| 情境 | 動作 |
|---|---|
| Issue 身分無法確認、GitHub 無權限或 CLI 不存在 | `blocked`，不推進 |
| 工作分支未綁定 Issue、與合約不符或落後預設分支 | `blocked`，需核對分支與來源 |
| Spec 需要但沒有 proposal/tasks | 回到 `openspec` |
| Architecture 新決策但無 ADR | `propose_adr` |
| ADR Proposed / Rejected / Superseded / Missing | `await_human_adr_approval` + `blocked` |
| 多個 PR 指向同個 Issue、Branch 上有未關聯 PR | 阻擋並要求釐清 |
| 工作區未提交、Branch 基準不可比較 | 阻擋並要求檢查 |
| PR HEAD 和本地同名 Branch SHA 不一致 | 阻擋，需同步 |
| CI 缺少/失敗、Check 無法查證 | `validation` + `blocked` |
| CI 通過但 PR 尚未合併 | `review` + `blocked`，等待人工 |
| PR 確認 mergedAt | `close`（仍須結案授權） |

## 已知限制（需在 P1 解決）

1. **ADR 合法核准**：目前只能辨識 Markdown Status，無法證明是人員所核准；不可將檔案中的 `Accepted` 等同已核驗的 reviewer approval。下一版加入有權限的 PR review/approval provenance 查核。
2. **OpenSpec 完成度**：目前的 `ready` 僅代表 proposal.md / tasks.md 存在，不是規格品質或所有 task 完成的證明。
3. **PR 列表上限**：目前查詢最多 100 筆，較大 Repo 需分頁或改用 Issue timeline 避免漏抓。
4. **CI 僅支援 GitHub check-runs 首頁**：大型專案須加入 pagination 與合併佇列 SHA 處理。
5. **分支比較**：從 GitHub 取得 default branch 名稱與遠端 SHA，與本地同名分支比較。淺複製、worktree 特殊布局或本地缺少最新 default SHA 時採保守阻擋，須先手動同步。
6. **人員審核**：沒有設定 Repo 的 GitHub Rulesets 就不具備強制性的 Merge Gate。本 Repo 的測試 Actions 只驗證工具程式；不代表其他產品 Repo 自動受保護。
